# 要求 — Giftia 送別ギフトの「決めきれない」を解決する

前提: 講座（Tech0 Step3-1）の Giftia ケースで、モック（Next.js＋FastAPI＋班の Azure MySQL）を作る。2026-11-17（火）の週までは手元のパソコンで動かし、その後 Azure にデプロイする予定（ADR-0009）。決済・ログインは対象外。
今回の開発①で実装するのは BR-02 と BR-04（の計測）。BR-01 は今の検索画面をそのまま使い、新しくは作らない（ADR-0008）。
元にした書類：班の「要求定義書」（2026-11-15 確定版。班の Google Drive）。数字の出典はケース資料の Exhibit 番号で書く。

## 誰が使うか
<!-- 利用者の立場・人数・利用場面 -->

- **贈る人**（顧客A）：職場の先輩（40代女性）が異動するので、同僚3人で 4,500円前後の送別の品を贈りたい。先輩とはあまり親しくなく、好みはよく知らない（要求定義書 3.1 候補1）
- **一緒に贈る同僚**（2人）：贈る人から相談を受け、候補を見て意見を返す

## 何に困っているか
<!-- 今の困りごと。できれば具体的な場面で -->

好みをよく知らない先輩への送別の品で「変なものを選んだ」と思われたくないのに、何なら変じゃないのか確信が持てず、その責任を自分ひとりで負いたくないので、候補を絞っても最後を決めきれない（のではないか）。（要求定義書 3.2）

- 「40代 女性 送別 プレゼント」で検索したが、絞れなかった（要求定義書 3.1）
- 送別シーンの購入率は 1.7% で、5つのシーンの中で最も低い（Exhibit 1 表2）

## できると嬉しいこと

提供価値（要求定義書 4.1）
- 選んだ理由を、あとで聞かれても説明できる状態で買える
- これを選んでいいのかという確認を、周りの人と一緒にできる

要求（要求定義書 4.2）

| 要求ID | 要求 | 優先度 |
| --- | --- | --- |
| BR-01 | 好みをよく知らない相手でも、相手との関係や予算を手がかりに、候補を数個まで絞れる | 中 |
| BR-02 | 一緒に贈る人の賛成を集めて、自分ひとりの判断にせず決められる | 高 |
| BR-03 | 選んだ理由を、あとで「なんでこれにしたの？」と聞かれても説明できる状態で決められる／変なものと思われないものを選べる | 中（高にするか検討中。下の「未決」） |
| BR-04 | 送別シーンで、候補を決めるまでの迷いを減らし、購入率を 1.7% → 2.3% に引き上げる | 高 |

## 成功の定義
<!-- 何がどうなれば成功と言えるか -->

要求定義書 6章から。

- Phase1（このモック）：他班など3人1組（5組ほど）に一連の機能を使ってもらい、スムーズに決められたか、購入したくなったかを聞き取る。見る指標は、共有URLを受け取った同僚の**投票率**（賛成を送った人の割合）と**コメント率**（理由かひとことを送った人の割合）
  - 成功：投票率 80% 以上・コメント率 50% 以上
  - 仮説が間違い：投票率 50% 以下、またはコメント率 30% 以下
- Phase2（本番を想定）：実装したあとの1か月間で、送別シーンの購入率 1.7% → 2.3% 以上。機能を使った送別の購入率が、使わなかった送別より上がらなければ、仮説が間違い

## 受入基準（受入テストの元。1行1基準）
<!-- テスト設計.mdの受入テスト（A-xx）と1対1で対応させる -->
- AC-01：贈る人が、今の検索画面で検索した結果から候補を3つまで選び、共有URLを作れる（BR-02。検索そのもの＝BR-01 は今の画面のまま）
- AC-02：同僚が、共有URLを別のパソコンで開き、名前を入れずに（匿名）候補に賛成し、賛成した候補には理由（選択肢）を、候補ごとにひとこと（自由記述）を送れる（BR-02。賛成の数は #20、理由の必須は #19 で相談中）
- AC-03：贈る人が、回答した人数・1位と理由・候補ごとのひとことを1つの画面で見られる。賛成数・理由の数は出ない（BR-02。ADR-0012）
- AC-04：贈る人が購入ボタンを押すと、共有リストの番号つきで記録が残り、共有を使った購入ボタンの数を数えられる（BR-04）
- AC-05：集まった声から Giftia が1位の商品を必ず1つ決め、選ばれた理由（「賛成多数」または「決め手：◯◯」）が表示される（BR-03。ADR-0012）
