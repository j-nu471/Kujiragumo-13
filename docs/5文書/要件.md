# 要件 — Giftia 送別ギフトの「決めきれない」を解決する

前提: 今回は Web アプリのモック（PoC）を作る。2026-11-17（火）の週までは手元のパソコンで動かし、その後 Azure にデプロイする予定（N-06、ADR-0009）。元にした書類：班の「要件定義書」（2026-11-15 確定版）の 2章（Phase1）・3章（要求→要件マッピング）・4章（機能・画面・API）・5.2（データの定義）・6.2（順位の付け方）。
開発①で作るのは、班のワイヤーフレームの ②〜⑤ と、① 条件を入れる（BR-01）のうち予算と贈るシーンで絞るところ（F-01・F-02、ADR-0019）。① は最初、今の検索画面をそのまま使う予定だった（ADR-0008）。続く ③〜⑤ に進むために、検索結果の商品を「候補に入れる」機能を作る（F-03）。

## 非機能要件

| ID | 要件 | 受入基準 |
| --- | --- | --- |
| N-01 | DB の接続情報は `.env` だけに置き、Git・画面・ログに出さない | `git ls-files` に `.env` がない。画面の JS に接続情報がない |
| N-02 | 班のDBの既存7つの表（`products` など）は変えない。新しい表を足すだけ | 既存の表の列が、開発の前とあとで同じ（`DESCRIBE` で確かめる） |
| N-03 | 受け取った値は SQL の文字列につなげず、`%s` で渡す | コードに `f"...{入力}..."` の形の SQL がない（レビューで見る） |
| N-04 | 共有リストの番号は推測できないものにする（連番にしない） | 番号が UUID（36文字）になっている |
| N-05 | ひとこと（自由記述）は200文字まで。理由は6つの選択肢（`wanted`・`fits`・`memorable`・`practical`・`safe`・`none`）のどれかだけを受け付ける（ADR-0013。#19 で相談中）。名前などの個人情報は受け取らない・保存しない（ADR-0010） | 201文字のひとこと、または選択肢にない理由を送ると、保存されずエラーが出る |
| N-06 | 2026-11-17（火）の週までは手元で動けばよい。その後 Azure にデプロイする予定なので、**デプロイで変わるもの（API の URL、画面の URL、CORS の許可先、DB の接続情報）はコードに直接書かず、環境変数か、開いているページから取る**（ADR-0009） | 今週：`npm run dev` と `uvicorn main:app --reload` で通しで動く。来週：コードに `localhost` を直接書いた箇所がない（`lib/api.ts` 26行目の初期値は除く） |

## 実装時に確定するパラメータ（方針は決定済み）
- 候補の上限：3つ
- 「候補に入れる」を出す商品：検索結果（開いた時点の人気のギフトを含む）に出ている商品。人気順で1ページ20件。ページを移っても、選んだ候補は残る（ADR-0019）
- シーンのボタン：「すべて」「送別」「誕生日」「お礼」「母の日」「父の日」「結婚祝い」「出産祝い」「お中元」「お歳暮」（「すべて」以外は `product_scenes.scene_tag` と同じ文字。ADR-0019）
- ひとことの文字数の上限：200文字（N-05）
- 理由の選択肢：`wanted`（本人が欲しがっていた（まだ持っていなさそう））・`fits`（贈る相手にぴったりだと思う）・`memorable`（特別感があって記念になりそう）・`practical`（実用的で使ってもらえそう）・`safe`（好みを選ばず、誰からも喜ばれそう）・`none`（とくにない）（ADR-0013。#19 で相談中）
- 点数：賛成1つ＝5、理由の重みは `wanted` 4・`fits` 3・`memorable` 2・`practical` 1・`safe` 1・`none` 0（ADR-0012。使ってみて見直す）
